### Introduction {#introduction}

Building a reliable software platform requires more than just writing code—it demands a structured approach to testing and a well-thought-out PR workflow. Without these, projects can quickly become unmanageable, riddled with bugs, and burdened with security risks. {#building-a-reliable-software-platform-requires-more-than-just-writing}

Imagine launching a new feature, only to find it breaking key functionality in production. Now imagine the chaos of scrambling to fix it post-release. A robust testing strategy prevents these scenarios, ensuring that every deployment is stable, scalable, and secure. {#imagine-launching-a-new-feature-only-to-find-it-breaking}

In this post, we explore how a carefully planned test suite and a structured PR workflow can help developers maintain high-quality code while optimizing costs. {#in-this-post-we-explore-how-a-carefully-planned-test}

### The Case for Comprehensive Testing {#the-case-for-comprehensive-testing}

Testing is often seen as an overhead expense, but in reality, it’s an investment in long-term stability. The key is not just to test but to test **smartly**—balancing coverage, cost, and execution time. {#testing-is-often-seen-as-an-overhead-expense-but-in}

#### A Pragmatic Approach to Testing {#a-pragmatic-approach-to-testing}

A pragmatic testing approach recognizes that not all tests are equally valuable or necessary in every scenario. The key is prioritizing tests based on their impact and likelihood of catching critical bugs. This involves a multi-layered approach: {#a-pragmatic-testing-approach-recognizes-that-not-all-tests-are}

1. {#testing-at-different-levels-each-level-of-testing-serves-a} **Testing at Different Levels:**
   
   
   
   - {#each-level-of-testing-serves-a-distinct-purpose-from-catching} Each level of testing serves a distinct purpose, from catching regressions in the UI to validating individual functions.
   - {#instead-of-running-every-test-in-every-pipeline-execution-we} Instead of running every test in every pipeline execution, we optimize when and how different test types are executed.
1. {#balancing-speed-and-depth-running-a-full-e2e-suite-on} **Balancing Speed and Depth:**
   
   
   
   - {#running-a-full-e2e-suite-on-every-commit-would-be} Running a full E2E suite on every commit would be inefficient, slowing down the development cycle.
   - {#instead-lightweight-unit-tests-run-automatically-on-every-pr-while} Instead, lightweight unit tests run automatically on every PR, while deeper E2E and visual tests run only on staging environments.
1. {#parallelizing-tests-for-efficiency-we-split-tests-across-multiple-environments} **Parallelizing Tests for Efficiency:**
   
   
   
   - {#we-split-tests-across-multiple-environments-and-execute-them-in} We split tests across multiple environments and execute them in parallel to minimize feedback time.
   - {#for-example-web-and-mobile-e2e-tests-run-in-separate} For example, web and mobile E2E tests run in separate environments to avoid bottlenecks.
1. {#focusing-on-critical-path-coverage-prioritizing-test-coverage-for-core} **Focusing on Critical Path Coverage:**
   
   
   
   - {#prioritizing-test-coverage-for-core-user-flows-ensures-that-the} Prioritizing test coverage for core user flows ensures that the most important functionalities remain stable.
   - {#tests-should-focus-on-areas-prone-to-frequent-changes-such} Tests should focus on areas prone to frequent changes, such as authentication, payments, and critical UI elements.
1. {#using-change-detection-to-run-relevant-tests-instead-of-running} **Using Change Detection to Run Relevant Tests:**
   
   
   
   - {#instead-of-running-all-tests-on-every-update-we-use} Instead of running all tests on every update, we use Git’s diffing capabilities to identify affected areas.
   - {#for-instance-if-only-the-dashboard-component-is-modified-we} For instance, if only the dashboard component is modified, we trigger Cypress and unit tests specific to that component.
1. {#preventing-flaky-tests-from-blocking-deployments-flaky-tests-can-create} **Preventing Flaky Tests from Blocking Deployments:**
   
   
   
   - {#flaky-tests-can-create-frustration-and-erode-confidence-in-the} Flaky tests can create frustration and erode confidence in the test suite.
   - {#we-implement-retry-mechanisms-and-quarantine-unstable-tests-until-they} We implement retry mechanisms and quarantine unstable tests until they are fixed.

### A Breakdown of Our Testing Strategy {#a-breakdown-of-our-testing-strategy}

#### 1\. End-to-End (E2E) Testing {#end-to-end-e2e-testing}

E2E tests simulate real user interactions, ensuring that core workflows function as expected. Given their complexity, they tend to be expensive but are invaluable for catching regressions. {#e2e-tests-simulate-real-user-interactions-ensuring-that-core-workflows}

- {#web-cypress-75-month-provides-a-robust-ui-testing-framework} **Web:** Cypress (**$75/month**) provides a robust UI testing framework.
- {#mobile-maestro-250-month-offers-a-streamlined-mobile-automation-solution} **Mobile:** Maestro (**$250/month**) offers a streamlined mobile automation solution.

#### 2\. Unit Testing {#unit-testing}

At the heart of any test suite, unit tests validate individual components and functions. These are relatively low-cost but crucial in maintaining core logic. {#at-the-heart-of-any-test-suite-unit-tests-validate}

- {#api-jest-25-month-efficiently-tests-backend-logic} **API:** Jest (**~$25/month**) efficiently tests backend logic.
- {#mobile-react-native-testing-library-25-month-ensures-mobile-ui} **Mobile:** React Native Testing Library (**~$25/month**) ensures mobile UI integrity.
- {#web-react-testing-library-25-month-validates-frontend-behavior} **Web:** React Testing Library (**~$25/month**) validates frontend behavior.

#### 3\. Visual Regression Testing {#visual-regression-testing}

A visually appealing app can break with even a minor CSS update. Visual regression testing ensures UI consistency across updates. {#a-visually-appealing-app-can-break-with-even-a-minor}

- {#web-chromatic-150-month-detects-unintended-ui-changes} **Web:** Chromatic (**$150/month**) detects unintended UI changes.
- {#mobile-sherlo-150-month-offers-mobile-focused-visual-testing} **Mobile:** Sherlo (**$150/month**) offers mobile-focused visual testing.

#### The Cost of Quality Assurance {#the-cost-of-quality-assurance}

Balancing test coverage and cost is essential: {#balancing-test-coverage-and-cost-is-essential}

- {#full-test-coverage-e2e-unit-visual-700-month-8-400} **Full test coverage (E2E, unit, visual):** $700/month ($8,400/year)
- {#partial-test-coverage-excluding-visual-350-month-3-900-year} **Partial test coverage (excluding visual):** $350/month ($3,900/year)

While it may seem expensive, these costs pale in comparison to the potential fallout of undetected critical issues in production. {#while-it-may-seem-expensive-these-costs-pale-in-comparison}

An organized branching strategy is crucial for maintaining workflow efficiency. Without clear structure, teams risk merging unstable features, delaying releases, or encountering complex conflicts. {#an-organized-branching-strategy-is-crucial-for-maintaining-workflow-efficiency}

#### Feature Branch Workflow {#feature-branch-workflow}

Each feature branch follows a strict validation process before integration: {#each-feature-branch-follows-a-strict-validation-process-before-integration}

1. {#develop-engineers-create-feature-branches-off-development-and-push-changes} **Develop:** Engineers create feature branches off `development` and push changes.
1. {#test-unit-tests-run-automatically-to-catch-regressions} **Test:** Unit tests run automatically to catch regressions.
1. {#stage-once-validated-the-branch-merges-into-stage-triggering-e2e} **Stage:** Once validated, the branch merges into `stage`, triggering E2E and visual tests.
1. {#review-approve-the-code-undergoes-peer-review-for-quality-assurance} **Review & Approve:** The code undergoes peer review for quality assurance.
1. {#deploy-upon-approval-the-changes-merge-into-main-and-roll} **Deploy:** Upon approval, the changes merge into `main` and roll out to production.

#### Smart Test Execution Using Change Detection {#smart-test-execution-using-change-detection}

Rather than running all tests on every commit, we leverage Git’s `diff` command to selectively trigger relevant test suites: {#rather-than-running-all-tests-on-every-commit-we-leverage}

```
git diff --name-only main feature-branch -- app        # Run Maestro & unit tests
git diff --name-only main feature-branch -- shared     # Trigger all tests
git diff --name-only main feature-branch -- dashboard  # Run Cypress & unit tests
git diff --name-only main feature-branch -- widget     # Run Cypress & unit tests
```

By running only necessary tests, we optimize CI/CD performance, reducing execution time and cloud compute costs. {#by-running-only-necessary-tests-we-optimize-ci-cd-performance}
